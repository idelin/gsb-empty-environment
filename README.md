# multires — 多资源领取库

一次满足作业所需的**全部**资源：要么原子地拿到所有资源，要么整体排队，
绝不出现"拿到一半后阻塞"的部分占用。Go 1.11+，仅依赖标准库。

```go
p := multires.New(map[string]int64{"cpu": 8, "mem": 32})

rel, err := p.Acquire(ctx, multires.Demand{"cpu": 2, "mem": 4})
if err != nil { /* ctx 取消/超时，未占用任何资源 */ }
defer rel() // 幂等释放，归还全部资源并唤醒等待者
```

## 设计

- **全有或全无**：`Acquire` 只在所有资源的可用量都充足时才授权；
  等待期间 `InUse` 不变，不持有任何部分资源（`multires.go` 的
  `scheduleLocked`/`canSatisfyLocked`）。
- **可取消**：传入的 `ctx` 取消即把请求移出队列并重新调度，不残留占用；
  取消与授权竞争时按成功处理，避免泄漏。
- **队列次序 + 可满足优先**：调度器按 FIFO 扫描，可满足的请求优先授权；
  不可满足的队首可被后面的请求**跳过**，每被跳过一次计数 +1。
- **队首屏障**：队首累计被跳过 3 次（`DefaultMaxSkips`，可用
  `SetMaxSkips` 调整，<=0 表示严格 FIFO）后成为屏障，禁止任何后续请求
  再跳过它，直到它被满足或取消。
- **释放回调**：`SetOnRelease` 注册的回调在**锁外**执行，可安全重入
  `Acquire`/`Release`/`Stats`；回调触发前等待队列已重新调度，
  即等待者对释放出的资源有优先权。
- **配额调整**：`SetQuota` 调大会唤醒等待者；调小不抢占已持有资源，
  可用量（`Quota-InUse`）可为负，仅阻止新授权，直到归还使占用回落。

## 饥饿条件分析

**问题来源**：允许跳过意味着"大请求在队首、小请求流不断到达"时，
大请求可能被无限绕过——经典队首阻塞下的饥饿。

**本实现的有界等待保证**：队首每被绕过授权一次，`skipped` 单调递增；
达到 3 次后队首成为屏障，此后任何释放出的资源都只能累积、
不会被后来的请求截走。因此在以下前提下，队首的等待是有界的
（至多再等待当前持有者归还出足够资源的时间）：

1. **持有者最终都会归还**。库不强制回收（无租约/超时），泄漏的授权
   会永久阻塞等待者——调用方必须用 `defer rel()` 或超时控制。
2. **需求量 ≤ 总额度**。超过配额的请求永远无法满足；若它成为队首
   屏障会堵住整个队列，只能靠 `ctx` 取消解除（见 `SetQuota` 可临时
   调大配额让其通过）。
3. **取消可传播**。`ctx` 取消会把请求从队列移除并立即重新调度，
   屏障队首被取消后被挡住的可满足请求即刻恢复。

**吞吐与公平的权衡**：屏障生效期间，本可满足的小请求也被阻塞，
吞吐下降；`maxSkips` 越大越偏吞吐，越小越偏公平（0 = 严格 FIFO）。
跳过计数按"实际被后来的授权绕过"累计，空扫描不计数，且计数随请求
在队列中前进——不存在计数被重置导致的活锁。

**配额缩减**：`SetQuota` 调小是非抢占式的。已持有者的资源不被强制
回收，`Available` 可能为负；新授权被阻止直到占用自然回落到配额内。
这避免了抢占式回收的级联失败，但意味着缩减的生效时间取决于持有者
的归还速度——同样依赖前提 1。

## 测试

```sh
GO111MODULE=on go test -race ./...
```

覆盖：全有或全无（无部分占用）、可满足请求跳过队首、跳过 3 次后的
队首屏障与解除、取消移除等待者、取消屏障队首后恢复调度、释放回调
重入（回调内再次 Acquire/Release/Stats 不死锁）、配额缩减（负可用量、
占用回落后唤醒、调大即唤醒）、取消与授权竞争、释放幂等。
