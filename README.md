高速广域网存在轻微包乱序时，传统 3-DupACK 丢包检测会频繁误判丢包并过早触发拥塞窗口折半，而单靠 RTO 超时又会让尾部丢包（Tail Loss）白白停顿数百毫秒；此外接收端可能随时反悔（SACK Reneging）丢弃此前已选择性确认的乱序段，发送端若直接把 SACK 段当永久送达就会导致数据永久缺失。为传输栈交付可导入的 Go TCP RFC 6675 + RFC 8985（RACK-TLP）记分板与恢复引擎。组件维护按 32 位回绕序列号（RFC 1982 模算术）索引的已发送段记分板（支持分段部分确认、SACK、重传、累计 ACK 与 DSACK 乱序识别）。规则：1）SACK 处理须支持多达 4 块乱序/重叠 SACK 区间，正确识别首个落在 `SND.UNA` 之前的 DSACK 块并按 RFC 8985 扩大 `reo_wnd` 乱序容忍窗（受 `SRTT` 上限约束，且在无持续乱序后按恢复轮次衰减）；2）实现 RACK 基于时间的丢包检测（记录最新确认/SACK 包的发送时间 `xmit_ts` 与结束序列号，标记满足 `seg.xmit_ts + reo_wnd <= rack.xmit_ts` 且被后发包越过的未确认段为丢包）并与 RFC 6675 `IsLost`（超过 3 段或 `3*SMSS` 字节）及精确在途估算 `SetPipe()` 协同工作；3）实现 TLP（尾丢包探测）定时器调度与探测包发送，在收到首个有效 ACK 时自动取消或触发恢复；4）当收到 RTO 超时时严格按 RFC 6675 清空全部 SACK 标记（应对接收端 SACK Reneging！）并按重传优先级输出下一批待发段。验收覆盖 32 位序列号跨 `0xFFFFFFFF -> 0` 回绕、DSACK 触发 `reo_wnd` 扩张抑制乱序误判、尾包丢失由 TLP 迅速挽救、SACK Reneging 后 RTO 完整重传以及 `pipe` 估算与 `cwnd` 恢复周期边界。
