Kubernetes 调度器的 `PodTopologySpread` 在引入 `minDomains`、`matchLabelKeys`、`nodeAffinityPolicy` 与 `nodeTaintsPolicy` 后，各字段间交互极为细微：忽略污点策略会把不可调度的隔离区算进最小域计数导致 `minMatch=0` 误判，而未对多个 `DoNotSchedule` 约束同时取交集则可能放行违背第二条约束的节点。为集群调度框架交付可导入的 Go 拓扑分布过滤与打分组件。输入为待调度 Pod（含标签、NodeSelector/NodeAffinity、Tolerations 与多条 `TopologySpreadConstraint`）及集群节点和已运行 Pod 列表（含 Terminating 状态 Pod 不计入、仅匹配同命名空间与约束 `labelSelector` 且结合 `matchLabelKeys` 交集过滤）。规则：按每条约束各自的 `nodeAffinityPolicy`（Honor/Ignore，默认 Honor）与 `nodeTaintsPolicy`（Honor/Ignore，默认 Ignore，其中 Honor 仅匹配 Pod 容忍全部 `NoSchedule`/`NoExecute` 污点的节点！）筛选出有资格的拓扑域并统计各域匹配 Pod 数；对 `DoNotSchedule` 约束，若符合条件的拓扑域数小于 `minDomains`（未设默认 1），缺失域按计数 `0` 参与 `globalMin` 计算，节点仅当其具备该 `topologyKey` 标签且放入后 `domainCount + 1 - globalMin <= maxSkew`（多条硬约束须同时满足）时通过过滤；对 `ScheduleAnyway` 约束按加权偏斜差值计算可比归一化打分（优先计数更小域，同分按节点名序确定性排序）。验收覆盖 `minDomains` 触发虚拟 0 域、`nodeTaintsPolicy=Honor` 与 `Ignore` 结果反转、`matchLabelKeys` 动态收窄匹配集、多条硬约束叠加、缺标签节点淘汰及软硬约束混合打分。
