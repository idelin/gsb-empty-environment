# Adaptive Batch Size Regulator（自适应批大小调节器）

向量化执行引擎的自适应调度组件。监控当前查询的 L1/L2 CPU 缓存命中率与数据行大小，
动态调整每批处理行数：行较宽时自动收缩至 **256**，行极窄时放大至 **4096**，
使单批数据足迹保持容纳在 L1 缓存内，维持缓存热态、避免缓存颠簸（thrashing）。

零依赖 TypeScript 实现，使用 Node.js 原生 TypeScript 类型剥离运行，
测试基于 Node.js 内置测试框架（`node:test` + `node:assert`）。

## 环境要求

- Node.js >= 22.6（原生运行 `.ts`，无需编译步骤；开发环境验证版本：v23.9.0）

## 结构

- `src/cache.ts` — 模拟的 L1/L2 组相联缓存层级（LRU），提供命中率观测
- `src/regulator.ts` — `AdaptiveBatchSizeRegulator`：静态目标（行宽 → 刚好容纳 L1 的最大 2 次幂，夹在 [256, 4096]）+ 动态反馈（L1 命中率低则减半、热态良好则翻倍）
- `src/engine.ts` — `VectorizedEngine`：按批多趟扫描行存宽表，每批结束后向调节器上报观测
- `test/adaptive-batch-regulator.test.ts` — Node.js 内置测试（10 个用例）
- `examples/demo.ts` — 运行样例

## 运行

```bash
npm test       # node --test test/*.test.ts
npm run demo   # node examples/demo.ts
```

## 运行样例（`npm run demo` 输出节选）

验收边界场景：超宽宽表（16 列 × 8B = 128B/行），内存带宽受限环境
（L2 仅 64KB，1024 行批足迹 128KB 超出 L2，颠簸直达内存）：

```
=== 超宽宽表查询（128B/行，自适应开启） ===
batch | rows | batchSize | footprint | fitsL1 | L1 hit | L2 hit | memReads
    0 | 1024 |      1024 |    131072 |  false |   0.0% |   0.0% |     8192
    1 |  512 |       512 |     65536 |  false |   0.0% |  75.0% |     1024
    2 |  256 |       256 |     32768 |   true |  75.0% |   0.0% |      512
    ...
最终批大小=256  估计停顿周期=4011008  checksum=65258278.5

=== 超宽宽表查询（128B/行，固定 batch=1024 对照组） ===
batch | rows | batchSize | footprint | fitsL1 | L1 hit | L2 hit | memReads
    0 | 1024 |      1024 |    131072 |  false |   0.0% |   0.0% |     8192
    ...（每批都颠簸，L1 命中率 0%，每批回读内存 8192 行）
最终批大小=1024  估计停顿周期=13107200  checksum=65258278.5

=== 极窄表查询（8B/行，自适应放大） ===
batch | rows | batchSize | footprint | fitsL1 | L1 hit | L2 hit | memReads
    0 | 1024 |      1024 |      8192 |   true |  96.9% |   0.0% |      128
    1 | 2048 |      2048 |     16384 |   true |  96.9% |   0.0% |      256
    2 | 4096 |      4096 |     32768 |   true |  96.9% |   0.0% |      512
    ...
最终批大小=4096  估计停顿周期=1073152  checksum=16269852.5
```

调节器感知到内存带宽受限（L1 命中率 0%、每批 8192 次内存回读）后，
将批大小从 1024 动态下调至 256（256 × 128B = 32KB，刚好容纳进 L1），
L1 命中率恢复至 75%（多趟扫描中仅首趟为必然失效），
估计停顿周期相比固定 1024 降低约 **3.3 倍**，且查询结果（checksum）完全一致。
