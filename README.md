# chunkstore

内容寻址的分块 KV 存储，仅使用 Go 标准库。所有文件都落在 `Open(dir, ...)` 调用方指定的目录中。

## 设计

- **分块与去重**：值按固定大小（默认 4 MiB）分块，每块以其 SHA-256 命名存于
  `chunks/<hex[0:2]>/<sha256>`。相同内容只存一份，多个值天然共享块。
- **元数据事务**：`meta.json` 记录每个 key 的有序块哈希列表、总长度，以及每个块的
  引用计数。每次 Put/Delete 先克隆元数据、应用变更，再通过
  “写 `meta.json.tmp` → fsync → rename → fsync 目录” 原子提交。
- **引用计数回收**：覆盖、删除、回滚只处理引用计数降为 0 的块——元数据直接知道是哪些，
  常规写入路径从不扫描数据目录。
- **读校验**：`Get` 逐块重算 SHA-256 并与内容寻址的文件名比对，任何篡改/腐坏都会报错。
- **故障注入点**：`Hooks.AfterChunkWrite`（第 n 块写完后）与 `Hooks.BeforeMetaCommit`
  （提交事务前），返回错误即中止并回滚，测试借此模拟磁盘故障。

## 写入流程（Put）

1. 逐块读取输入，每块先写 `<hash>.tmp`，fsync 后 rename 为正式名，再 fsync 所在目录；
   已存在的块直接跳过（共享）。
2. 任何一步失败：删除本次 Put 新建的块（它们从未被提交的元数据引用，必为孤儿），
   已存在的共享块绝不触碰，元数据保持不变。
3. 全部块落盘后，原子提交新元数据（新 key 的块引用 +1，被覆盖旧值的块引用 -1）。
4. 提交成功后，删除引用计数为 0 的块文件。

## 崩溃恢复与断电保证的边界

**保证的部分**

- 元数据提交是原子的：任何时刻 `meta.json` 要么是旧版本、要么是新版本，不会出现
  半写状态（rename 原子性 + 前后 fsync）。`Open` 时发现残留的 `meta.json.tmp`
  说明崩溃发生在 rename 之前，直接丢弃临时文件，以上一次提交的 `meta.json` 为准。
- 块先于元数据落盘（fsync + rename + 目录 fsync 都在提交前完成），因此**已提交的
  元数据永远不会引用缺失的块**（在正常文件系统语义下）。
- 已提交的块不会被后续失败的 Put 删除：回滚只删本次新建且未被引用的块。
- 读取路径逐块校验 SHA-256，提交后发生的静默数据腐坏（bit rot、掉电后部分写）
  会在读时被发现，而不是返回错误数据。

**不保证的部分（边界）**

- **崩溃孤儿块**：若进程在“块已落盘、元数据未提交”之间崩溃，这些块成为孤儿。
  为了不扫描全部数据，它们不会被自动回收，只泄漏空间、不影响正确性；
  需要时可另行做一次离线 GC（遍历 chunks 目录对比引用计数）。
- **回收的持久性**：提交成功后删除零引用块是 best-effort；此时崩溃只是少删了几个
  文件（同样只泄漏空间）。
- **文件系统语义**：保证建立在“rename 原子、fsync 生效”的常规本地文件系统上。
  断电后文件系统自身未兑现 fsync（如某些写缓存配置、网络文件系统）时，
  上述原子性不成立——但读路径的逐块校验仍能检测出数据损坏。
- **meta.json 本身腐坏**：若已提交的 `meta.json` 被外部破坏，`Open` 会报错拒绝启动，
  不做自动修复（无冗余副本）。

## 使用

```go
s, _ := chunkstore.Open("/path/to/store", chunkstore.Options{ChunkSize: 4 << 20})
err := s.Put("key", reader)   // 或 s.PutBytes("key", data)
data, err := s.Get("key")     // 逐块校验 SHA-256
err = s.Delete("key")         // 只回收无引用块
```

## 运行

```sh
go test -v ./...   # 测试（含故障注入、边界、崩溃恢复用例）
go run ./cmd/demo  # 演示：去重、共享块安全、失败回滚、腐坏检测
```
