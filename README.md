# 联合多数成员切换模拟器（Go 标准库 / 单进程事件模拟）

用 Go 标准库实现的视图戳（view-stamped）复制协议 + Raft 式联合共识（joint
consensus）成员切换，运行在一个单进程事件模拟器上：通信（消息投递、丢弃、
延迟）、故障（节点崩溃/重启）与时间（虚拟时钟）全部由模拟器控制。

## 协议要点

- **视图（view）**：每条消息都带视图号。节点拒绝来自更旧视图的消息；
  同一视图内每个节点只投一次票；迟到投票（视图号小于当前视图）被丢弃。
- **配置链**：唯一合法的配置迁移路径是
  `Stable(A) -> Joint(A,B) -> Stable(B)`。
  联合阶段（Joint）内，选举与提交都需要**旧集合多数 + 新集合多数**。
  直接从旧多数跳到互不相交的新多数会被两处拒绝：
  leader 侧 API（`ProposeDirectSwitch`）与 follower 侧配置守卫
  （`Config.canTransitionTo`，见 `config.go`）。
- **提交规则**：leader 只按计数提交本视图条目（更早条目随之提交）；
  法定人数按当前生效配置判定——联合阶段即双重多数。
- **中断恢复**：leader 当选后先追加本视图 no-op 锚定；发现日志中有已提交的
  联合条目时自动补发 `Stable(B)` 完成条目，完成被中断的切换。
  不在已提交稳定配置中的 leader 自动卸任。

## 安全性论证（证据）

1. **每视图至多一个 leader**：同一视图内节点只投一票，选举法定人数与任何
   其他法定人数（稳定期：多数；联合期：双重多数）相交，故两候选者不可能
   同时获胜。
2. **Leader 完整性**：投票前做日志 up-to-date 检查（比较末条目的
   (view, index)）。已提交条目存在于提交法定人数的每个节点上；选举法定
   人数与提交法定人数相交（联合期在两个集合上分别相交），故新 leader 的
   日志不落后于任何已提交条目。
3. **配置链唯一**：`canTransitionTo` 只接受上述链；`Stable(A)->Stable(B)`
   （A≠B，可能互不相交）被所有 follower 拒绝，因此旧多数与新多数永远不会
   各自独立提交——不存在"双脑"窗口。
4. **运行时不变量**：模拟器在每一步后检查 (a) 所有节点已提交日志互为前缀；
   (b) 每次提交都记录了法定人数证书（`Sim.Certs`），且证书满足提交时配置
   的（联合）多数条件。随机故障测试（5000 步，随机丢包/延迟/崩溃/重启/
   选举/重配置）全程保持该不变量。

## 活性论证（证据）

若旧集合多数与（联合期）新集合多数存活且消息最终在有界延迟内送达，则：
某候选者终将获得一个独占视图并集齐法定人数（测试中以选举超时触发）；
联合条目与完成条目各需一次相应法定人数复制，故切换在有界虚拟时间内完成。
`TestReconfigurationCompletesLiveness` 断言切换在 500 tick 内完成，且旧集合
全部崩溃后新集合仍能独立提交命令；`TestInterruptedSwitchRecovery` 断言
leader 在联合提交后、完成条目传播前崩溃时，下一视图 leader 经联合选举
恢复并完成切换。

## 运行

```sh
go run .        # 四个演示场景（正常切换 / 拒绝直接切换 / 迟到投票 / 中断恢复）
go test -v ./... # 安全性与活性测试
```

文件：`config.go`（配置与法定人数）、`message.go`（消息与日志条目）、
`node.go`（协议状态机）、`sim.go`（事件模拟器与安全检查）、
`main.go`（演示）、`reconfig_test.go`（测试）。
