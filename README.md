# 事务消息模拟器（Transactional Outbox + 崩溃恢复 + 故障注入）

模拟可重复投递的订单事件处理：**订单更新**与**待发通知登记**在同一事务中完成，
通知至少投递一次（ACK 可丢失），接收方按通知标识去重。

## 结构

- `src/log.ts` — 内存事务日志（WAL，视为持久存储）与故障注入器。
  记录类型：`BEGIN / ORDER_APPLY / EVENT_MARK / OUTBOX_ADD / COMMIT / OUTBOX_ACK`。
- `src/system.ts` — 订单服务（事务性 Outbox）、崩溃恢复、接收方去重、可丢 ACK/丢投递的信道。
- `src/simulator.ts` — 测试台：逐持久化边界注入崩溃、注入 ACK/投递丢失、组合场景，并校验不变量。

## 关键设计

- **原子性**：订单更新、事件去重标记、Outbox 通知写在同一事务（`BEGIN..COMMIT`）。
  恢复时只重做已提交事务，未提交记录整体回滚 —— 订单更新与通知登记要么都生效，要么都不生效。
- **崩溃恢复**：崩溃丢弃全部易失状态（订单表、已应用事件集、待发队列），重放日志重建。
- **幂等消费**：事件按 `eventId` 去重（去重状态与同事务持久化），重复投递直接跳过。
- **通知不丢**：通知 ID 由事件 ID 确定性派生；ACK 丢失或崩溃导致 `OUTBOX_ACK` 未持久化时，
  通知留在待发队列被重投；接收方按 `notificationId` 去重，业务效果恰好一次。
- **故障注入模型**：在每条日志追加前触发一次性崩溃。"边界 k" = 恰好 k 条记录持久化、
  第 k+1 条丢失。k 取 0..N-1 覆盖所有运行中边界；最后一个边界（全部追加完成后崩溃）
  由每个场景结束时的额外 `crashAndRecover()` 覆盖。

## 验证的不变量（每个场景）

1. 每个事件的订单更新恰好应用一次（订单事件带非幂等增量，重复应用会立即暴露）。
2. 每个订单最终总额等于期望值。
3. 接收方对每个通知恰好应用一次（无重复、无遗漏）。
4. 结束时 Outbox 无残留（通知不会永久遗漏）。

## 运行

```sh
npm run build   # 需要 tsc（本仓库无运行时依赖）
npm test        # node dist/simulator.js
```

当前结果：18 条日志记录 → 18 个运行中崩溃边界 + 末尾边界，叠加 ACK/投递丢失与组合场景，
共 282 项检查全部通过。
