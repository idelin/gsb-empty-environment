分析型查询优化器尝试用已物化的聚合视图 `V` 改写新聚合查询 `Q` 时，表面看 `Q` 的分组列是 `V` 分组列的子集似乎总能直接上卷（Rollup），但实际存在四类隐蔽陷阱：`V` 的 `HAVING` 条件若已提前剪掉某些细粒度分组，`Q` 即使想按更粗维度聚合也绝不可复用（因为被剪掉的组已无法还原！）；`Q` 需要 `AVG(x)` 时必须从 `V` 中同时找到 `SUM(x)` 和 `COUNT(x)` 做加权合并（绝不能对各组的 `AVG` 再求平均！），且若 `x` 可空则不能用 `COUNT(*)` 替代 `COUNT(x)`；`Q` 的 `WHERE` 残余谓词只能引用 `V` 输出的分组列；以及当 `Q` 含全局无 `GROUP BY` 聚合且输入表为空时，直接对空视图二次聚合与标准 SQL 单行 `COUNT=0, SUM=NULL` 的语义必须完全吻合。为查询优化器交付可导入的 Go 聚合视图匹配与补偿改写引擎。输入为基表模式（列类型与可空标记）、候选物化视图集合 `V_1..V_n`（各含基表、`WHERE` 区间/等值合取谓词、`GROUP BY` 列集、聚合输出列集及可选 `HAVING` 条件）与目标聚合查询 `Q`。规则：判定每个视图是否对 `Q` 语义可重用（校验基表一致、视图 `WHERE` 蕴含查询 `WHERE` 且残余过滤列全部暴露在视图分组列中、`Q` 分组列被 `V` 分组列覆盖或函数依赖覆盖、视图 `HAVING` 不会裁掉 `Q` 需要的源组、全部聚合函数均可在 `V` 输出上精确再聚合——含 `COUNT` 上卷改 `SUM`、`AVG` 改 `SUM/COUNT`、`MIN`/`MAX` 上卷、且对非可空/可空列严格区分 `COUNT(*)` 与 `COUNT(col)`！）；若可改写则输出规范补偿查询计划及求值结果，否则给出精确不可重用原因分类。验收用含大量 `NULL`、空表与不同 `HAVING` 阈值的数据集对比直接查基表与查物化视图改写结果，覆盖 `AVG` 加权合并、可空列 `COUNT(col)` 拒绝借用 `COUNT(*)`、`HAVING` 截断拦截及空表无分组全局汇总一致性。
