# 租赁排程器 (rental-scheduler)

在"同型号设备可互换 + 累计工时达到阈值须占工位维护"的约束下, 求**拒单损失最小**的排程方案(最多 15 单)。

## 规则建模

- 每个订单有固定时间窗 `[start, end)`、所需设备型号与拒单损失 `penalty`, 执行期间独占一台设备。
- 同型号设备完全可互换; 每台设备的**累计工作时长跨订单保留**。
- 若 `累计时长 + 订单时长 > 阈值`, 该设备必须先在维护工位完成维护(时长 `maintenanceDuration`), 维护后累计清零。
- 维护是**显式调度事件**, 必须占用指定工位(工位总数有限、同一时刻只能维护一台设备);
  **设备空闲时间不会被自动算作维护**——只有时间线中的维护事件才能清零累计时长。
- 支持**预防性维护**: 未超阈值时也可以提前维护(例如工位稍后繁忙时有用)。
- 订单时长本身超过阈值的订单不可服务, 必拒。

## 算法

按订单开始时间做分支定界 DFS(指数级但 15 单规模足够快, 示例约 1s):

1. 每个订单分支为"拒绝(计入损失)"或"分配到某台可行设备"; 状态相同的同型号设备去重。
2. 需要维护时, 在 `[设备空闲时刻, 订单开始 - 维护时长]` 内枚举候选维护槽位
   (取可行区间端点: 下界、上界、工位占用区间端点), 同时尝试预防性维护分支。
3. 记忆化剪枝: 相同 `(订单序号, 各设备可用时刻/累计工时, 工位占用)` 状态只保留历史最小损失。
4. `verify()` 按时间线重放校验方案: 只有显式维护事件能清零累计工时, 空闲不清零。

## 使用

```bash
npm run build          # 或: tsc -p tsconfig.json
node dist/src/main.js              # 内置 15 单示例
node dist/src/main.js scenario.json # 从 JSON 加载场景
npm test               # 需先 build; 运行 dist/tests/run-tests.js
```

场景 JSON 格式见 `scenario.json`:

```json
{
  "stationCount": 1,
  "models": [{ "name": "excavator", "units": 2, "threshold": 10, "maintenanceDuration": 4 }],
  "orders": [{ "id": "O1", "model": "excavator", "start": 0, "end": 6, "penalty": 50 }]
}
```

## 输出

- 总拒单损失与被拒订单列表;
- 每台设备的租赁 + 维护时间线(维护标注工位号, 租赁标注执行后累计工时);
- 每个工位的维护时间线;
- 自动对方案做规则校验。

## 文件

- `src/scheduler.ts` — 类型、求解器 `solve()`、校验器 `verify()`
- `src/main.ts` — CLI 入口与时间线打印
- `src/sample.ts` — 内置示例场景
- `tests/run-tests.ts` — 断言测试(含"空闲不算维护""预防性维护""工位竞争"等用例)
