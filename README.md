Kubelet 节点驱逐管理器（Eviction Manager）在内存或本地磁盘逼近阈值时决定驱逐哪些 Pod，绝不是简单按内存占用从大到小杀进程：1）Pod QoS 等级必须严格依据所有业务容器与 InitContainer 的 CPU/内存 `requests`/`limits` 推导——仅当每个容器均同时设置 CPU 与内存且 `request == limit`（缺省 request 自动继承 limit！）才为 `Guaranteed`；仅当全部容器均未设置任何 CPU 与内存的 `request` 与 `limit` 才为 `BestEffort`；其余为 `Burstable`！2）面对 `memory.available` 与 `nodefs.available` 两种不同资源信号，驱逐排序规则截然不同：内存压力必须按**超出 `requests.memory` 的超额量（`usage - request`）**排序——第一梯队包含所有 `BestEffort`（视 `request=0`）与 `usage > request` 的超额 `Burstable` Pod，梯队内先按 PriorityClass 升序（低优优先被杀！）、同优先级按超额量降序；第二梯队包含 `Guaranteed` 与 `usage <= request` 的守规 `Burstable` Pod，先按 PriorityClass 升序、再按超额量降序（即离上限最近/实际占用高者优先）；而磁盘压力（`nodefs.available`）下无 request 概念，直接按实际本地存储用量降序结合 PriorityClass 排序！3）支持同时配置 `evictionHard`（瞬间触发）、`evictionSoft` + `evictionSoftGracePeriod`（必须连续超过宽限期才触发，中途只要有一次采样回落到安全区则立刻重置计时器！）以及 `evictionMinimumReclaim`（触发驱逐后须持续驱逐直到预计回收量达到阈值加最小回收量，防止在阈值边缘反复抖动！）；4）跳过已处于 `Terminated`/正在优雅终止中的 Pod，绝不可重复驱逐已标记驱逐的 Pod。为节点运行时交付可导入的 Go Kubelet 驱逐管理器与 QoS 推导包。验收覆盖含 InitContainer 的三类 QoS 推导、超额量排序反超总用量（低总用量超额 `Burstable` 优先于高总用量守规 `Guaranteed` 被杀！）、PriorityClass 覆写顺序、软阈值中途恢复清零宽限期以及 `evictionMinimumReclaim` 批量回收与防重复驱逐。
