# 乐观并发状态仓库（TypeScript，零依赖）

为异步操作提供“先乐观应用、确认后提交、失败精准撤销”的状态管理原语。
不使用任何响应式框架或第三方依赖；Node.js 内置测试运行器验证。

## 需求对照

| 要求 | 实现 |
| --- | --- |
| 乐观补丁先行，失败只撤销自身 | `submit` 先入待确认队列并在乐观视图生效；`reject` 仅丢弃该操作，以已确认日志重放其余操作 |
| 后续用户编辑必须保留 | 回滚不是“逆补丁恢复旧快照”，而是从日志中剔除失败操作后整体重放，排队中的 B/C 不受影响 |
| 确认按 操作ID + 版本 匹配 | `confirm(id, ackBaseVersion)` 必须同时命中 ID 与登记时的 `baseVersion` |
| 状态操作可回放 | 已确认状态是补丁日志的纯折叠：`replay()` / `log()` / `hydrate()` |
| 读者看不到事务中间态 | 补丁原子（scratch 试算成功后整体替换）；`read()` 只暴露已确认快照，未确认操作仅出现在 `view()` |
| A 写后 B 写，A 失败不能覆盖 B | 提交按排队顺序重放；A 被剔除后 B 的补丁仍对当前已确认状态生效 |
| 重复确认幂等 | 已提交操作再次 ACK 返回 `already_committed`，不新增日志、版本不增长 |
| 迟到旧响应不回退新状态 | 版本不匹配 / 已拒绝操作的迟到 ACK 返回 `conflicted`，状态原样不动 |

## 模型

- **补丁（Patch）**：一组有序原子步骤（`set` / `remove` / `add`），在克隆出的草稿上执行，
  任一步失败抛 `AtomicPatchError`，已有状态零改动。
- **队列**：操作按提交顺序排队。队首未决时，后续操作即使先收到确认也保持
  `pending`（返回 `blockedBy`）；队首失败则跳过它并自动推进后续已确认操作。
- **版本**：已提交版本 = 已确认日志条数。`submit` 时 `baseVersion` 必须等于当前已提交版本。
- **可见性**：`read()` = 已确认（其他读者）；`view()` = 已确认 + 待确认（提交者自己的乐观视图）。
  返回快照均做深拷贝并递归冻结。

## 运行

需要 Node >= 22.18（原生执行 TypeScript；开发环境为 Node v23.9.0）。

```bash
npm test      # node:test 内置测试运行器
npm run example
```

离线环境无需 `npm install`，零依赖。若需要静态类型检查，可在有网络处
`npm i -D typescript @types/node` 后 `npx tsc --noEmit`（配置见 `tsconfig.json`）。

## 样例输出（节选）

`npm run example` 完整演示「A 乐观写 → B 再写 → B 先确认被阻塞 → A 失败仅撤销自身、
B 自动提交 → B 重复确认幂等 → A 的成功 ACK 迟到被忽略 → 日志回放重建」：

```
A 自己看到的乐观视图: { version: 0, state: { title: 'A 的标题', count: 0 } }
其他读者此时看到: { version: 0, state: { title: '原始', count: 0 } } （未确认，不可见）
服务端先确认 B → { kind: 'pending', id: 'op-B', blockedBy: [ 'op-A' ] }
A 失败后读者看到: { version: 1, state: { title: '原始', count: 10 } }
B 重复确认 → already_committed（日志条数仍为 1）
A 迟到成功 ACK → conflicted（状态保持 { title: '原始', count: 10 }）
```
