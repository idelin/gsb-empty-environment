BGP RPKI ROA 只能校验源自治系统（Origin AS）是否合法，却对中间转发路径上的**路由泄漏（Route Leak，即把从供应商或对等方学到的路由违法转运给另一供应商或对等方！）**完全无能为力；IETF ASPA（Autonomous System Provider Authorization）验证算法通过每个自治系统发布的“授权上游供应商集合 `SPAS(AS)`”来精确检测 `AS_PATH` 中的无谷违例，算法边界极其精巧：1）**预处理与非法路径拦截**：对输入 `AS_PATH` 首先拒绝任何包含 `AS_SET` 或空路径的通告（直接判 `Invalid`！），再折叠所有连续重复的 AS_PATH Prepending 得到去重路径 `[AS_1, AS_2, ..., AS_N]`（注意：绝不能把非相邻重复的真实环路错误折叠！）；2）**单跳关系函数 `hop(A, B)`**：若 `A` 发布了 ASPA 记录且 `B in SPAS(A)` 返回 `Provider+`；若 `A` 发布了 ASPA 记录（哪怕 `SPAS(A)` 仅含 `AS 0` 表示无任何上游供应商！）且 `B not in SPAS(A)` 返回 `NotProvider+`；若 `A` 未发布任何 ASPA 记录返回 `NoAttestation`！3）**四类 BGP 会话角色的上下行峰谷验证**：定义**上行最大峰 `max_up_ramp`**（从源端 `AS_N` 往左最长无 `NotProvider+` 的区间）与**下行最大峰 `max_down_ramp`**（从收包端 `AS_1` 往右最长无 `NotProvider+` 的区间），以及不含 `NoAttestation` 的严格全确认峰 `min_up_ramp` / `min_down_ramp`：- 从 **Customer / Lateral Peer / RS-Client** 收到的路由必须**全程单调上行**（绝不可包含任何下行 Provider->Customer 跳！）：若存在任意一对相邻 `(AS_{i+1} -> AS_i)` 返回 `NotProvider+` 立刻判 `Invalid`；若全部相邻跳均为 `Provider+` 判 `Valid`；否则判 `Unknown`！- 从 **Provider** 收到的路由允许先从源端上行到顶峰、经至多 1 条 Peer 跳或单顶峰 AS 再单调下行至收包端：当 `max_up_ramp + max_down_ramp < N` 时**必然存在隐藏谷底泄漏，立刻判 `Invalid`**（哪怕中间存在 `NoAttestation` 也绝不可误判 `Unknown`！）；当 `min_up_ramp + min_down_ramp >= N` 时判 `Valid`；其余情况判 `Unknown`！4）支持透明 Route Server（RS 不把自己加入 `AS_PATH`）与 Sibling/Complex 关系边界及输出导致 `Invalid` 或 `Unknown` 的精确违规跳下标与诊断说明。为骨干网路由安全控制面交付可导入的 Go IETF ASPA 路由泄漏验证引擎。验收覆盖 Prepending 折叠 vs `AS_SET` 拒绝、`AS 0` 无供应商记录、Customer/Peer 路径零下行校验、Provider 路径顶峰单跳容忍 vs `max_up + max_down < N` 必漏 `Invalid`（含混有 `NoAttestation` 时仍能证伪！）以及全边界穷举对照。
