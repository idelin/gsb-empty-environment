Kubelet 的 `TopologyManager` 联合 `CPUManager` 与多个 `DeviceManager`（GPU、SR-IOV 网卡等）为高性能计算 Pod 求解最优 NUMA 亲和掩码，核心难点在于多资源提示提供者（Hint Providers）的位掩码笛卡尔积合并、策略裁决与作用域差异：1）每个提示提供者返回一组 `TopologyHint{NUMANodeAffinity bitmask, Preferred bool}`（空数组表示该提供者无拓扑偏好；含单个 `nil` 掩码表示无法满足任何亲和！）；合并全部提供者提示时，必须遍历所有组合求按位与（`&`）并过滤掉结果为 0 的互斥组合——若任何非空提供者组合按位与全为 0，则退化为返回不满足亲和的空掩码 `Preferred=false`！2）从所有可行合并掩码中严格按 Kubelet 规范选出最佳掩码：先比是否 `Preferred == true`（仅当参与该组合的所有提供者提示均为 `Preferred` 时合并结果才为 `Preferred`！）？注意：实际规范允许配置 `prefer-closest-numa-nodes`（跨 NUMA 距离矩阵最小平均跳数优先！），默认则优先选覆盖 NUMA 节点数最少（`popcount` 最小）且 `Preferred == true` 优先于同宽度 `Preferred == false`，同宽同优再按掩码数值最小确定性决胜！3）严格实施三种策略：`best-effort` 始终准入并返回最佳掩码；`restricted` 仅当最佳掩码的 `Preferred == true` 时准入（否则拒绝 Pod 准入！）；`single-numa-node` 强制要求最佳掩码同时满足 `Preferred == true && popcount(mask) == 1`！4）支持 `container` 作用域（逐容器独立求解并扣减可用资源）与 `pod` 作用域（整 Pod 所有业务容器汇总为一个联合资源需求统一对齐；且必须考虑 InitContainer：串行执行的 InitContainer 资源峰值若超过业务容器需求须确保单次可对齐，并在 InitContainer 结束后复用已分配的同掩码独占 CPU/设备池而非双倍扣减！）。为容器节点运行时交付可导入的 Go NUMA `TopologyManager` 提示合并、资源预留与准入仲裁包。验收覆盖多提供者位掩码笛卡尔积合并、`restricted` vs `single-numa-node` vs `best-effort` 准入边界、`prefer-closest-numa-nodes` 距离打破平局、`pod` vs `container` 作用域以及 InitContainer 资源复用不双扣校验。
