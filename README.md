# optimistic-replay-store

TypeScript 状态库：在已确认基线之上乐观地重放待确认操作，并按服务端回执（可乱序到达）做对账。

## 模型

- 状态为 `Map<objectId, value>`；操作有三种：`create` / `update` / `delete`。
- 客户端维护初始快照 + 按提交顺序排列的完整操作日志。
- 可见状态始终由**单次有序重放**导出：

  ```
  view = replay(initialSnapshot, nonRejectedOps in submission order)
  ```

## 为什么不是「基线 + 待确认」两段式重放

回执可能乱序：一个已确认操作可能排在它依赖的、仍未收到回执的前驱之后
（例如 `update a` 的回执先于 `create a` 到达）。若把「已确认基线」和
「待确认操作」分成两段重放，会改变交互操作的相对顺序，导致已确认操作被
静默跳过。因此视图按提交顺序单趟重放；已确认基线（`getBaseline()`）单独
维护，仅表示服务端已确认的部分。

## 对账语义

- **接受**：操作进入已确认集合，基线随之更新。
- **拒绝**：操作从日志中移除，剩余后继在初始快照上重新按序重放。
  引用了已不存在对象的后继（如被否决的 `create` 之后的 `update`）被标记为
  `dependency` 失败并跳过；`create` 撞已存在对象标记为 `conflict`。
- **绝不还原整份旧快照**：拒绝只移除该操作本身，其他成功操作（已确认或
  仍在待定）的效果完整保留。
- 失败集合在每次回执后重算：若导致依赖失败的操作后来被否决（如 `delete`
  被拒），后继会自动恢复生效。

## 验证

- `test/store.test.ts`：乱序回执、拒绝后重放、依赖失败与恢复、冲突、
  非法回执等单元测试。
- `test/fuzz.test.ts`：确定性 PRNG 生成随机操作序列，模拟串行服务端裁决，
  将回执**随机打乱**逐条送达；每条回执后都与串行参考模型
  （`serialReference`：按提交顺序、剔除被拒操作后的单趟应用）比对状态与
  失败集合；另验证同一批回执的不同打乱顺序收敛到同一终态。

## 运行

```sh
npm install   # 需要 typescript (devDependency)
npm test      # tsc 编译到 dist/ 并运行全部测试
```
