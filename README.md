# 多副本多值寄存器（MV-Register）

这是一个只依赖 Go 标准库的单进程事件驱动示例。多副本保存多个并发值，版本向量判断因果关系；系统不会用墙钟时间自动选择“较新”的值。

## 结构

- `mvreg/vector.go`：版本向量及其偏序比较。
- `mvreg/register.go`：状态型多值寄存器、写、显式解决和状态合并。
- `sim/simulator.go`：单进程确定性事件模拟器，控制时间、通信、停机故障和恢复。
- `example/main.go`：并发写、墙钟不吞并、显式解决、解决传播、故障延迟投递的完整样例。
- `*_test.go`：全部行为测试均通过 `go test` 运行。

## 核心语义

- 初始读取为空。
- 本地写立即生成 `(Origin, Nonce, VersionVector)`，其中 `Origin` 是副本 ID，`Nonce` 是该副本单调递增的计数。
- 写操作的版本向量包含该副本当前已观察到的全部版本，因此后继写会覆盖它已观察的旧版本。
- 合并时保留所有向量互不支配的条目；被某个版本向量严格支配的条目被删除。
- 同一写通过重复消息重放不会产生重复值。
- `Resolve(value)` 是显式解决操作：它不是后台自动仲裁，而是在当前观察集合上产生一个新的因果后继版本。
- 解决状态通过普通状态合并传播；已经被解决向量支配的旧分支再次送达也不会复活。
- 墙钟时间仅用于调度事件和网络延迟，不参与版本向量比较，所以墙钟较大但无因果关系的写不能吞并其他值。

## 运行样例

```sh
go run ./example
```

输出：

```text
t=1   A: write red at {A:1}
t=200 B: write blue at {B:1}
t=201 A: send to B scheduled at t=202
t=202 B: received state from A; values=[red,blue]
t=203 B: send to A scheduled at t=204
t=204 A: received state from B; values=[red,blue]
t=205 C: failed
t=205 A: resolve purple at {A:2,B:1}
t=206 A: send to C scheduled at t=207
t=207 B: send to C scheduled at t=208
t=209 C: recovered
t=209 C: received state from A; values=[purple]
t=209 C: received state from B; values=[purple]

final values:
A: [{purple A 2 map[A:2 B:1]}]
B: [{red A 1 map[A:1]} {blue B 1 map[B:1]}]

```

`B` 最终仍保留冲突，因为它没有收到 `A` 的解决结果；收到解决结果的 `C` 与之后的旧分支重放合并后仍只有 `purple`。

## 模拟器 API

```go
s := sim.New[string]([]string{"A", "B", "C"}, sendDelay)
s.Run([]sim.Event[string]{
    {Time: 1, Kind: sim.Write, Target: "A", Value: "red"},
    {Time: 2, Kind: sim.Send, Target: "A", To: "B"},
    {Time: 3, Kind: sim.Fail, Target: "B"},
    {Time: 4, Kind: sim.Recover, Target: "B"},
    {Time: 5, Kind: sim.Resolve, Target: "A", Value: "purple"},
})
values := s.Read("A")
```

事件按 `(Time, 提交顺序)` 确定执行；没有 goroutine、随机数或真实网络。`Send` 捕获发送时刻的深拷贝快照，因此网络延迟不会让未来写“穿越”到旧消息中。

## 安全性论证

这里的安全性是：读取不会丢弃未被因果后继覆盖的已提交值，也不会让墙钟或重复消息改变因果结果。

1. 每个写或解决都有唯一 `(Origin, Nonce)`，其版本向量记录该操作直接或间接观察到的每个副本的最大计数。
2. 版本向量比较定义因果偏序：`x < y` 表示 `x` 的所有分量不大于 `y` 且至少一个严格小于；互不支配表示并发。
3. 状态合并是上下文的逐项最大值和条目的并集，然后删除被其他条目支配的条目。上下文最大值和条目按唯一键去重，使合并满足幂等、交换和结合，因此重复或乱序送达不会改变最终状态。
4. 两个并发写的向量至少在各自副本计数上互相超过，因此任一条目都不支配另一条目，两个值都会保留。
5. 后继写的向量包含其已观察版本的向量并推进本副本计数，所以后继严格支配旧条目，旧条目在包含两者的读取中被删除。
6. 显式解决在观察了冲突分支后产生新向量。若它的上下文包含各冲突向量，则该解决条目支配这些分支；解决状态传播后，旧分支重复送达也会再次被同一向量支配。
7. 墙钟字段不存在于寄存器状态中；模拟器只在事件调度层使用时间。因此大墙钟不会产生版本向量上的支配关系。

## 活性论证

这里的活性条件限定为：存活副本上的本地操作最终完成；在网络最终可达、停机故障最终恢复的条件下，发送的状态最终送达并促成收敛。

1. `Write` 和 `Resolve` 只修改本地内存，不等待网络；当副本处于 up 状态时在当前模拟时间立即完成。
2. `Send` 将发送时的深拷贝快照放入调度队列；若目标副本已恢复且到达投递时间，模拟器立即投递。
3. 消息在目标 down 时不会丢失，而是保留在队列中；恢复后成为可投递消息。
4. 只要存在未来的恢复事件使目标变为 up，调度器就会推进到该时间并投递所有到期消息。
5. 状态型合并幂等，因此超时重发和重复投递安全；所有已发送状态在最终连通的副本间重复交换后，因果上已解决的值会传播到可达副本。

停机状态保留副本内存；永久停机不属于活性前提，模拟器会保留无法投递的消息，而不会伪造投递成功。

## 测试

```sh
go test ./...
go test -v ./...
```

测试覆盖：

- 空读取和并发不同值同时保留。
- 后继写覆盖已观察版本。
- 因果旧快照不能复活新版本。
- 显式解决产生新向量并通过合并传播。
- 合并的幂等性、交换性、结合性。
- 快照深拷贝隔离。
- 模拟网络延迟、发送时刻快照、故障期间不投递、恢复后投递。
- 墙钟很大但因果并发时仍保留两个值。
- 事件日志和未知副本参数校验。
