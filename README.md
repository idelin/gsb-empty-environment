# 租赁排程器

同型号设备可互换的租赁排程：在累计工时维护约束下，求拒单损失最小的接单安排（实例最多 15 单）。

## 问题规则

- **同型号可互换**：订单只指定型号与固定时间窗 `[start, end)`，具体由哪台设备承接由排程决定。
- **累计工时跨订单保留**：每台设备维护后累计工作时长随接单累加，不随订单结束或空闲而清零。
- **阈值维护**：累计工时达到型号阈值后，设备必须先在其型号**指定的维护工位**上占用工位完成一次固定时长的维护，累计工时清零，才能继续接单。允许在未达阈值时主动维护。
- **空闲不算维护**：只有显式排在工位上的维护事件才能清零累计工时；设备闲置再久也不算维护完成。
- **工位容量**：同一工位同一时刻只能维护一台设备。
- **目标**：最小化被拒订单的损失之和。

## 算法

订单按开始时间排序后做分支定界（`solve`，见 `src/scheduler.ts`）：

- 每张订单分支为：分配到某台同型号空闲设备（直接接 / 先维护再接），或拒单。
- 维护槽位策略：在指定工位时间线上取**不晚于订单开始**的最早可用槽位；未达阈值时的"主动维护再接单"也作为一个分支，可规避后续工位冲突。
- 剪枝：当前损失超过已知最优即剪；剩余订单中任何设备（忽略工位冲突）都接不了的，其损失计入下界。
- 对称性约减：同型号且（可用时刻、累计工时）完全相同的设备只试一台。
- 精确性说明：在"维护安排在最早可行槽位"的放置策略下，接单/拒单决策是精确最优的；15 单规模可秒级求解。

`validateSchedule` 对结果做全规则校验（时间不重叠、阈值不超限、维护必须在指定工位且时长正确、累计工时只被显式维护清零、损失账目一致），演示与测试都会调用。

## 使用

```bash
npm install --save-dev typescript   # 需要 tsc（>= 4.x）
npm test          # 编译并运行规则测试
npm start         # 编译并运行示例，打印租赁/维护时间线
```

输入模型见 `ProblemInstance`（`src/scheduler.ts`）：`orders`（型号、时间窗、拒单损失）、`models`（阈值、维护时长、指定工位）、`units`（型号、初始累计工时）。输出 `ScheduleResult`：每张已接订单的租赁事件、每次维护事件（设备、工位、起止）、拒单列表、总拒单损失与各设备最终累计工时。

## 文件

- `src/scheduler.ts` — 求解器与校验器
- `src/index.ts` — 示例实例与时间线打印
- `src/scheduler.test.ts` — 规则测试（含"空闲不算维护""跨订单累计""工位不重叠"等用例）
