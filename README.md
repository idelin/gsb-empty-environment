分布式两阶段提交（2PC）在真实故障恢复中常采用 **Presumed Abort（推定中止）** 优化以省去中止路径的协调者强制刷盘，但一旦叠加只读参与者优化（`VOTE_READ_ONLY`）、协调者或参与者在任意 WAL 落盘点崩溃重启，以及处于 `IN_DOUBT` 悬疑态的参与者超时后单方面执行启发式提交/中止（Heuristic Commit/Abort），极易出现日志顺序违例（投票 `YES` 之前未强制落盘 `PREPARE` 导致重启后失忆违背原子性！）或启发式决策与协调者最终决议背离却无人察觉。为分布式事务中间件交付可导入的 Go 2PC Presumed Abort 协议与故障恢复模拟器。组件显式建模每个节点的易失内存状态、可崩溃回放的持久化 WAL（区分强制同步写 `ForceWrite` 与缓冲写 `FlushLater`）以及可丢包/乱序/重发的消息网络。规则：1）严格执行 WAL 落盘顺序不变式——参与者必须在发 `VOTE_YES` 前强制刷盘 `PREPARE`（记录锁与 undo/redo 意图），投票 `VOTE_READ_ONLY` 则立刻释放锁、不刷盘且退出第二阶段；协调者必须在发 `COMMIT` 前强制刷盘 `COMMIT_DECISION`（含非只读参与者列表），而决定 `ABORT` 时遵循 Presumed Abort 不强制写决定日志，崩溃恢复查无该事务记录时对参与者询问一律回复 `ABORT`！2）协调者收到全部非只读参与者 `ACK` 后写入 `END` 记录回收内存表；3）当 `IN_DOUBT` 参与者长期失联触及启发式超时，按配置执行 `HEURISTIC_COMMIT` 或 `HEURISTIC_ABORT` 并强制刷盘记录，后续收到协调者正式决议时精确比对：一致则正常完结，背离则绝不静默覆盖，必须上报 `HEURISTIC_MIXED`（部分提交部分中止）或 `HEURISTIC_HAZARD` 并保留冲突审计记录！验收用故障注入在每个协议步骤前后注入协调者崩溃、参与者崩溃、消息重复/丢失，验证无启发式干预时所有正常提交/中止严格满足全原子性（零部分提交！），验证 `VOTE_READ_ONLY` 零二次消息与零刷盘、Presumed Abort 失忆回 `ABORT` 以及启发式背离精确触发 `HEURISTIC_MIXED` 告警。
