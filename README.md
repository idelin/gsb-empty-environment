# 边缘缓存模拟器（屏障门控的配置分发）

模拟边缘缓存节点的配置更新传播：配置更新后，节点可以继续读旧值，
直到指定**屏障（barrier）**发布；此后读操作只能返回满足屏障的新版本，
否则等待。失效（invalidation）消息与数据（data）消息走同一总线，
允许乱序到达（失效可先于数据）。

## 语义

- **更新传播**：`Origin.update()` 广播失效消息；`Origin.pushData()` 单独
  广播数据载荷，因此失效天然可以先于数据到达。
- **屏障**：`Origin.publishBarrier()` 将屏障设为当前版本并广播。屏障在
  节点侧单调递增（旧屏障重放不会降低屏障）。
- **读路径**（`CacheNode.read()`）：
  - 已安装版本 ≥ 已知屏障 → 返回旧值（允许读旧值的窗口）。
  - 已安装版本 < 已知屏障 → 等待，直到满足屏障的数据到达（或超时
    抛出 `ReadTimeoutError`）。
  - 读在**完成时刻**重新校验屏障：屏障到达时仍在途的旧加载（late old
    load）不会返回过期值，而是转为等待。
- **每键状态机**：`SERVING`（正常服务）→ `STALE_OK`（已失效、屏障未到，
  可读旧值）→ `BLOCKED`（屏障已超过已安装版本，读等待）→ 数据到位后
  回到 `SERVING`。
- **重连**：节点离线期间消息被丢弃；`reconnect()` 进入 `RESYNCING`
  （读必须等待，因为节点可能错过了屏障），从 origin 快照全量同步后恢复
  `ONLINE`。离线期间节点按最后已知屏障提供最后已知值（它无法得知新屏障）。
- **连续两次更新**：`v2` 的数据晚于 `v3` 的失效与屏障到达时，节点会安装
  `v2` 但绝不对外提供（`v2 < barrier 3`），读一直等到 `v3`。

## 运行测试

```sh
npm test          # node tools/run-tests.js，零依赖，Node >= 16 即可
```

本环境无网络/无 tsc，测试通过 `tools/strip-types.js`（一个受控子集的
类型擦除加载器）直接执行 `.ts` 源码。有网环境下建议使用真实编译器：

```sh
npm install       # 安装 typescript / @types/node
npm run typecheck # tsc --noEmit
npm run build     # 编译到 dist/
```

## 布局

- `src/types.ts` — 消息/快照/读结果类型
- `src/bus.ts` — 确定性消息总线（手动投递、乱序投递、离线丢弃）
- `src/origin.ts` — 权威配置源：版本、屏障发布、快照
- `src/node.ts` — 缓存节点状态机（读路径、重连再同步）
- `test/` — 状态机、乱序、迟到旧加载、重连、连续两次更新的验证
