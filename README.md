# 认证恢复渠道双确认

用户替换恢复邮箱时，不能让尚未验证的新邮箱立即拥有找回权。写供Go身份宿主调用的换绑事务包，旧渠道确认与新渠道确认各自绑定同一变更摘要和期限，两者齐备才切换；撤回及并发第二次变更使旧证明失效。用事件排列测试确认乱序、响应丢失和期限边界，任何中间态仍保留明确的恢复渠道。

## 包结构

- `manager.go`：按账号串行的换绑事务管理器（`Manager`），持有当前生效渠道、至多一个进行中的事务和归档历史。
- `token.go`：变更摘要（digest）与确认证明（proof）的 HMAC 编解码，证明绑定 `(digest, role, deadline)` 三元组。
- `doc.go`：安全模型说明。
- `*_test.go`：事件排列测试与聚焦场景测试。

## 事务流程

1. `Provision` 为账号登记第一个已验证恢复渠道。
2. `Begin(accountID, newChannel, ttl)` 生成唯一变更 ID、变更摘要和期限；若已有进行中的事务，旧事务立即归档为 `superseded`，其全部证明失效。当前生效渠道不变。
3. `SendChallenge(changeID, role)` 向旧渠道（`RoleOld`）或新渠道（`RoleNew`）下发 HMAC 证明；响应丢失时重复调用返回完全相同的令牌，不产生新状态。
4. `Confirm(changeID, role, proof)` 校验签名、摘要、角色和期限并记录该角色确认；单边确认不改变恢复渠道。
5. 两个角色都确认后，恢复渠道原子切换为新渠道，事务归档为 `committed`。
6. `Revoke(changeID)` 显式撤回，证明立即失效，生效渠道保持不变。

## 安全不变量

- 任何中间态下 `ActiveChannel` 始终返回一个明确、有效的恢复渠道，新渠道在双方确认前不具备找回权。
- 证明只能用于其摘要、角色、期限完全一致的事务；跨事务、跨角色、篡改签名、过期、撤回、被取代的证明一律拒绝。
- 撤回或并发第二次 `Begin` 使旧事务的所有证明立即失效（分别返回 `ErrRevoked` / `ErrSuperseded`）。
- 期限语义为左闭右开：`now < deadline` 有效，到达或超过 `deadline` 即 `ErrExpired`。

## 测试

- `TestEventPermutations`：对 7 个可观测事件（开始、旧/新确认、撤回、响应丢失、并发第二次变更、到期）的全部 `7! = 5040` 种排列逐一执行，每个事件后断言：始终存在明确恢复渠道、失败操作无副作用、渠道切换必有对应的双确认已提交事务、失效证明不可再用。
- 场景测试覆盖正常流程、乱序确认（新渠道先确认）、期限纳秒级边界、响应丢失重发、撤回失效、并发取代、证明绑定与重放、参数校验。
- `TestConcurrentAccess` 在 `-race` 下以 8 个 goroutine 并发冲击同一账号，验证串行化与提交不变量。

```sh
go test -race ./...
go test -cover ./...
```
