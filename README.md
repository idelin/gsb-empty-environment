# pagedb — 基于 WAL 的页更新事务存储

纯标准库实现（Go 1.24+）。所有文件放在 `Open(dir)` 指定的目录中：

- `wal.log`：预写日志，记录 UPDATE（整页镜像）与 COMMIT 标记
- `pages.dat`：页文件，定长 4096 字节页框，按页 ID 寻址

## 设计

**WAL 记录**：`类型 | LSN | 事务ID | 页ID | 数据长度 | 数据 | CRC32`。
LSN 单调递增，同时充当页版本号。

**页**：`magic | 版本(=LSN) | 数据长度 | CRC32 | 数据`，校验和覆盖版本与数据。

**提交协议**（日志先于数据页持久化）：

1. `Set` 把 UPDATE 记录追加到 WAL（不 fsync），对读者不可见；
2. `Commit` 追加 COMMIT 记录并 **fsync WAL —— 这是提交点**；
3. 提交点之后才把暂存页写入 `pages.dat` 并 fsync。

**恢复**（`Open` 时执行）：

1. 顺序扫描 WAL，按事务分组，只重放带完整 COMMIT 标记的事务，
   未提交事务的 UPDATE 记录直接丢弃（不会暴露半个事务）；
2. 仅当 `记录LSN > 页版本` 时才应用该记录 —— 重放任意多次结果相同（幂等）；
3. 页校验和失败时按版本 0 处理，由 WAL 重建该页；
4. WAL 末尾残缺记录识别为**撕裂尾**并截断；若损坏点之后还能找到合法记录，
   判定为**中间损坏**，返回 `ErrMiddleCorruption`，绝不静默截断。

## 进程崩溃恢复

进程崩溃不丢已提交事务：提交点（WAL fsync）先于 `Commit` 返回。
崩溃发生在提交点前 → 事务整体不可见；崩溃发生在提交点后（含页刷盘
中途）→ 恢复时从 WAL 整体重放。页写一半是安全的：页校验和会发现撕裂页，
恢复用 WAL 中的整页镜像重建。

## 断电保证的边界

**保证**（依赖 OS/硬件遵守 fsync 语义）：

- `Commit` 成功返回后，事务在断电后仍然可见（WAL 已 fsync，目录项已 fsync）；
- 断电造成的 WAL 尾部撕裂写被 CRC 识别并截断；
- 断电造成的页撕裂写被页校验和识别，并由 WAL 重放修复。

**不保证**（超出用户态软件能力边界）：

- 磁盘/SSD 固件谎报 fsync（数据仍停留在易失写缓存却报告已持久化）；
- fsync 成功之后发生的介质位腐化（bit rot）、误定向写（misdirected write）——
  页校验和能**发现**但若无冗余副本则无法**修复**；
- 最后一条 WAL 记录恰好损坏与"撕裂尾"无法区分（二者都表现为末尾无合法记录），
  此时按撕裂尾截断——这是所有 CRC 尾检测方案的固有限制；
- 文件系统元数据损坏（如目录项丢失）超出 fsync 目录所能覆盖的范围。

## 故障注入

`DB.Fail.AfterWALSyncBeforePageFlush` 钩子在提交点之后、页刷盘之前触发，
返回错误即模拟进程当场崩溃，用于测试与演示恢复路径。
