HTTP/1.1 边缘代理与上游后端对 `Transfer-Encoding` 和 `Content-Length` 的边界容忍稍有分歧，就会引发 CL.TE、TE.CL 或多重 `Content-Length` 请求走私漏洞，导致长连接上第二条请求被夹带篡改。为反向代理数据面交付可导入的 Go RFC 9112 严格流式 HTTP/1.1 请求解析器（支持任意碎片化字节喂入，包括逐 1 字节增量输入与多请求流水线粘包！）。严格执行 RFC 9112 安全分帧与语法边界：1）请求行与头部字段仅接受严格 `CRLF`（拒绝裸 `LF` 与孤立 `CR`），拒绝字段名与冒号之间出现空格（`Header : val`）以及废弃的跨行折叠（`obs-fold`）；2）同时出现 `Transfer-Encoding` 与 `Content-Length` 必须立即判错拒绝；3）多个 `Content-Length`（含逗号分隔）仅当去掉合法 OWS 后所有数值完全一致且均为非负纯十进制数字（拒绝前导 `+`/`-`、空格夹杂与 `uint64` 溢出！）时折叠合并，否则拒绝；4）存在 `Transfer-Encoding` 时必须验证 `chunked` 出现且仅作为最末编码（拒绝 `chunked, chunked`、`chunked, gzip` 或非法空白变体），按分块规则解析十六进制块长（拒绝前导空格、`0x` 前缀、超长溢出）、严格校验块扩展语法、读取精确字节与结尾 `CRLF`，并在 `0` 块后解析合法尾部字段（Trailer）直至空行结束；5）长连接流水线解析完当前请求后，精准保留剩余缓冲字节供下一条请求无缝解析，绝不多吞或错位。验收用逐 1 字节与随机分片喂入覆盖 CL.TE、TE.CL、双不同 CL、双相同 CL、重复 `chunked`、裸 `LF`、头部名前空格、合法分块扩展加 Trailer 及多请求流水线精确切分。
