# mra — 多资源领取库

多资源（multi-resource）配额分配器：一次领取作业所需的**全部**资源，要么全部满足、要么排队等待，绝不"拿到一半后阻塞"。

## 语义

- **全有或全无（all-or-nothing）**：`Acquire` 只有在所有需求资源同时可满足时才授权；等待中的请求不持有任何部分资源，因此不存在"持有一半资源互相等待"的死锁形态。
- **可取消**：`Acquire(ctx, d)` 随 `ctx` 取消而出队，不残留、不泄漏；取消与授权竞争时，赢者决定语义（授权赢则调用方持有资源，需正常 `Release`）。
- **队列次序优先 + 有界跳过**：队首永远优先被考虑；队首暂不可满足时，允许后面可满足的请求"跳过"它，但每次跳过使队首 `skips+1`；队首累计被跳过 `MaxSkips`（默认 3）次后产生**队首阻塞**——不再允许任何超车，直到队首被满足。
- **释放回调可重入**：`OnRelease` 回调在内部锁释放之后调用，回调内可安全地再次 `Acquire` / `Release` / `SetQuota`，不会死锁。回调在释放者的 goroutine 上同步执行，不应长时间阻塞。
- **配额缩减**：`SetQuota` 允许把配额缩到当前用量之下。已持有者不受影响；在用量降回新配额之下前不再授权新请求。配额为 0 时任何正需求都不可行，`Acquire` 快速失败（`ErrExceedsQuota`）而非永久阻塞。

## 饥饿条件分析

**有界超越保证无饥饿（在正常释放前提下）。** 设队首请求为 H：

1. H 最多被跳过 `MaxSkips` 次。之后调度器拒绝任何越过 H 的授权，后续请求一律排在 H 之后等待。
2. 只要资源持有者最终在有限时间内释放，空闲容量单调累积到满足 H 为止——期间没有任何其他请求能抢走容量（跳过已关闭），故 H 必在有限时间内被满足。
3. H 出队后新队首重复同一论证。由归纳法，每个需求不超过配额的请求最终都会被满足 → **无饥饿**，且等待时间上界为"MaxSkips 次超车授权 + 持有者释放耗时"。

**仍可能饥饿 / 永久阻塞的条件：**

| 条件 | 行为 | 对策 |
|---|---|---|
| 需求 > 配额（含未知资源、配额为 0） | 永远不可满足 | 入库即快速失败 `ErrExceedsQuota`，不排队 |
| 持有者不释放（泄漏/死循环） | 全队阻塞 | 调用方负责配对 `Release`；`Acquire` 的 `ctx` 取消是等待者的逃生通道 |
| 配额缩减后长期低于排队需求 | 队首不可满足且触发队首阻塞 | 恢复配额（`SetQuota` 会重跑调度循环）或取消请求 |
| 释放回调永久阻塞 | 占用释放者 goroutine，后续 `Release` 延迟 | 约定回调必须快速返回；重入是安全的，阻塞不是 |

**取消语义**：取消只影响等待者自身（出队并返回 `ctx.Err()`），不回收已授予他人的资源；取消与授权竞争时若授权先发生，`Acquire` 返回成功，调用方须照常 `Release`，否则会造成上表第二种泄漏。

## API 摘要

```go
a := mra.New(map[string]int64{"cpu": 4, "mem": 8},
    mra.WithMaxSkips(3),
    mra.WithOnRelease(func(d mra.Demands) { /* 可重入 */ }),
)
err := a.Acquire(ctx, mra.Demands{"cpu": 2, "mem": 4}) // 全有或全无，可取消
a.Release(mra.Demands{"cpu": 2, "mem": 4})
a.SetQuota("cpu", 2) // 允许缩到当前用量之下
```

## 测试

```sh
go test ./... -count=1 -race
```

覆盖：全有或全无（等待者不持部分资源）、取消出队与取消/授权竞争无泄漏、跳过计数与三次后的队首阻塞、超配额快速失败、释放回调重入（回调内嵌套 Acquire/Release/SetQuota）、回调在授权之后执行、配额缩减到用量之下的阻塞与恢复。
