# 双故障注入分析与修补组件（Go 可导入包）

模块 `formal.local/h26-805a940eb5` 下的 `dfa` 包，面向安全启动自定义 VM，
在 **K=2 双故障预算** 下做攻击可达性分析、独立全枚举交叉对照，并求出
总代价最小、且保持正常输入可观察行为完全一致的保护插入方案。

## 平台与故障模型

- 程序至多 **32 条指令**；6 个布尔寄存器 `r0..r5`；1 个模 16 的 4 位计数器
  （`inc`/`dec`/`jz`）；至多 8 个公开输入位 `p0..p7`；执行步数上限 64。
- 指令：`inp`、`lds`（只读验签位）、`and`、`not`、`inc`、`dec`、`jz`、
  `jt`、`jmp`、`emit(tag)`、`unlock`、`halt`。
- 故障（每步至多一次，累计不超过 K=2）：
  - `skip` 跳过当前非 `halt` 指令（`halt` 不可跳过）；
  - `flip` 翻转一个布尔寄存器；
  - `invert` 反转一次 `jz`/`jt` 跳转方向。
- 验签结果位只读，任何故障都无法改写。

## 两份独立检查器

- `Attack` / `SecureAgainstK`：按 `(pc, 布尔寄存器, 计数器, 剩余故障数)`
  记忆化的 BFS，返回步数最浅、故障数最少的攻击见证 `[]Fault`。
- `ExhaustiveOracle`：无记忆化的故障计划全枚举递归，单步语义独立实现，
  不与 BFS/参考 VM 共享代码。
- `CrossCheck` 同时跑两者，并用参考执行器 `Replay` 独立重放见证，
  防止“同一份实现 bug 让两个检查器一起错”。

## 最小代价修补流程（`Analyze`）

1. 排除无故障原漏洞：零故障、验签失败却能 `unlock` 的程序直接拒绝。
2. 排除落在只读 ROM 半开区间 `[Start, End)` 内的候选插入点。
3. 按总代价升序枚举候选子集（候选 ≤8，最多 256 个），符号化拼接并链接，
   校验 32 条指令上限；插入只新增指令，绝不改写原 ROM 字节。
4. 对每个方案在全部无效验签输入上验证 K≤2 故障轨迹无法到达 `unlock`。
5. 在全部有效验签输入上验证 `unlock` 次数与完整 `emit(tag)` 序列逐位一致。
6. 用全枚举预言机交叉复核，返回第一个通过全部约束的最小代价方案。

## 关键安全结论

- 单点守卫 `SigGuard` 在 K=2 下必被击穿：两次条件反转（双跳）可分别越过
  插入守卫与原主校验；寄存器翻转同样可达。
- 任何共享单一计数器的关卡（`CounterGate`）都能被一次 `jz` 反转或一次
  `inc/dec` 跳过击穿，因此不构成 K=2 防护原语，包内已如实标注其边界。
- 可靠原语是 `TripleSigGuard`：三道瀑布式串联守卫，各自独立 `lds` 只读
  验签位，反转条件只会落入紧邻的 `halt`；每道守卫都需要一次独立故障，
  K=2 攻击者无法击穿。

## 快速开始

```go
prog := dfa.MustParse(asmText, 1) // 1 个公开输入位
candidates := []dfa.Candidate{
    {ID: "triple", Index: 0, Cost: 25, Gadget: dfa.TripleSigGuard([3]int{2, 3, 4})},
}
rom := []dfa.ROMRange{{Start: 3, End: 5}}
report, err := dfa.Analyze(prog, candidates, rom, dfa.DefaultBudgetK)
// report.Feasible 即最小代价可行方案（含修补后程序与交叉对照结论）
```

运行端到端演示（含双跳、寄存器翻转、ROM 排除、emit 一致性、全枚举复核）：

```
go run ./cmd/demo
```
