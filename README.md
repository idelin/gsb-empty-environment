# 分区备份检查器

给定多分区日志（每条记录带分区内提交版本 Seq）与跨分区事务的参与者清单，
求一个**可恢复截点**：每个跨分区事务要么在所有参与者的截点内完整提交，
要么整体不出现——绝不简单地"各分区各取最新版本"。

## 模型

- `Entry{Seq, TxnID, Kind, Key}`：分区日志条目，`Kind` 为 `Data`/`Commit`/`Abort`，`Seq` 即提交版本。
- `Txn{ID, Participants}`：跨分区事务及其完整参与者清单。
- `Cut`：分区名 -> 截点版本，包含所有 `Seq <= frontier` 的条目。

## 截点有效性（`ValidCut`）

1. **原子性**：任一事务的 Commit 标记落在部分参与者截点内、部分之外 => 无效。
2. **完整性**：截点内不允许存在"有 Data 但无 Commit"的事务数据（未决或已中止）。

## 算法（`RecoverableCut`）

从各分区最新版本出发，迭代回滚直到不动点：

- 提交标记只覆盖部分参与者 => 该事务在所有参与者处整体排除；
- 截点内含无提交标记的数据 => 回滚到该事务最早的 Data/Commit 之前。

回滚只排除 Data/Commit，无害的 Abort 标记保留。得到的是不超过当前状态的
**最大**可恢复截点（有效截点构成格，逐分量最大值唯一）。

## 证据输出（`Analyze`）

被排除事务按参与者给出证据：`Missing`（分区毫无痕迹）、`Undecided`
（已收到数据但事务未决）、`LateCommits`（提交标记存在但在截点之后，即迟到提交）、
`Aborted`。

## 验证

`checker_test.go` 用枚举法验证：随机生成小规模事务集合（3 分区、1~3 事务，
2000 组），枚举全部候选截点，断言构造算法的结果等于所有有效截点的逐分量最大值。

## 运行

```sh
go test ./...   # 枚举验证 + 针对性用例
go run .        # 演示场景：级联回滚 + 证据报告
```
