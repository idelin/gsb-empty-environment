# bpmatch — 精确带权二分图匹配（值班任务分配）

仅用 Go 标准库实现的精确求解器。给定任务集合、员工集合、可选边及
**有符号整数收益**，按以下优先级求解：

1. **最大化已分配任务数**（基数优先，负收益边绝不因此被舍弃）；
2. 在基数最大的方案中**最大化总收益**；
3. 仍并列时，按任务 ID 升序排列员工 ID 列表，取**字典序最小**者；
   未分配任务用哨兵表示，哨兵**大于一切员工 ID**（JSON 中为 `null`），
   即"能分就分，空位是最后的选择"。

ID 为字符串，按字节序比较。每人至多一项任务，每项任务至多一人。

## 构建与测试

```sh
go build ./cmd/bpmatch
go test ./...
```

## 命令行

```sh
bpmatch solve  [-in input.json]  [-out result.json]          # 求解（默认标准输入/输出）
bpmatch update [-in input.json]  [-out result.json] \
    (-add TASK=EMP:PROFIT | -del TASK=EMP)                    # 增/删单条边后重解
bpmatch verify -in input.json -sol result.json                # 独立核验结果
```

### 输入 JSON

```json
{
  "tasks": ["t1", "t2"],
  "employees": ["alice", "bob"],
  "edges": [{"task": "t1", "employee": "alice", "profit": -4}]
}
```

- 引用未知 ID、空 ID、重复 ID：报错；
- 同一对 `(task, employee)` 的**重复边**：收益一致则合并，冲突则报错；
- `update -add` 对已存在的边执行**改价**（幂等），`-del` 删除不存在的边报错。

### 输出 JSON

```json
{
  "cardinality": 3,
  "total_profit": 0,
  "tasks": ["t1", "t2", "t3"],
  "employees": ["alice", "bob", "carol"],
  "assignment": ["alice", "bob", "carol"],
  "matches": [{"task": "t1", "employee": "alice", "profit": -4}],
  "min_vertex_cover": {"tasks": ["t1", "t2", "t3"], "employees": []},
  "potentials": {"source": -6, "sink": 0, "tasks": {"t1": -4}, "employees": {"alice": 0}}
}
```

- `assignment` 与 `tasks` 平行，`null` 表示未分配（哨兵）；
- `min_vertex_cover` 与 `potentials` 是可独立核验的最优性证据（见下）。

## 为什么结果可以被独立核对

`bpmatch verify` 执行以下检查（也可由任何第三方程序复现）：

1. **结构**：分配只使用输入边、员工不重复、收益与基数自洽；
2. **最小顶点覆盖（基数最优性）**：检查覆盖集真的覆盖每一条输入边，
   且 `|覆盖| = |匹配|`。由 Kőnig 定理，任意匹配的大小不超过任意顶点
   覆盖的大小，相等即证明不存在更大的匹配——**这就是"无法分配更多
   任务"的可核对证据**。覆盖集由最终匹配的残量可达集构造：
   从未匹配任务出发沿交错路（非匹配边去、匹配边回）得集合 Z，
   覆盖 =（不在 Z 中的任务）∪（在 Z 中的员工）；
3. **对偶势（收益最优性）**：在最终匹配对应的残量网络
   （源→任务→员工→汇，任务→员工边费用为 `-profit`，反向边取负）
   上，输出势 π 满足对每条残量边 `(u,v,c)` 都有 `π[u] + c ≥ π[v]`。
   沿任意环求和即知残量网络无负费用环，故该流是同流量下费用最小
   （收益最大）的流；
4. **穷举复算**：当 `(E+1)^T ≤ 3×10^6`（覆盖 7×7）时，独立枚举全部
   匹配，逐一比对基数、总收益与字典序方案。

## 增量更新

`update` 支持增/删单条边。更新后对**新实例完整重解**，因此"更新结果
与重新求解一致"在构造上成立；测试还会把更新后的结果与穷举参考逐一
比对（含删除当前匹配边的场景）。

## 算法与复杂度

记 `T`=任务数，`E`=员工数，`M`=边数，`K`=最大匹配数 ≤ min(T,E)，
`V = T+E+2`。

| 阶段 | 方法 | 时间 |
|---|---|---|
| 基数 + 收益 | 单位容量最小费用流，连续最短路增广（Bellman-Ford，允许负费用），**只要存在增广路就增广，与路径费用无关** | `O(K · V · (M+T+E))` |
| 字典序 | 按任务序贪心：每个候选员工做一次可行性判定（受约束重解），未分配为哨兵兜底 | `O((M+T) · K · V · (M+T+E))` |
| 顶点覆盖 | 交错路 BFS（Kőnig） | `O(T+M)` |
| 对偶势 | 超级源 Bellman-Ford | `O(V · (M+T+E))` |
| 增量更新 | 应用变更后完整重解 | 同上 |
| 穷举参考（测试/核验） | 枚举全部匹配 | `O((E+1)^T · T)` |

空间 `O(V + M)`。字典序阶段的正确性：归纳可知当前前缀总能扩展为某个
最优解，因此每个任务至少有一个可行选择（含未分配哨兵）。
