邮件安全网关在验签 DKIM（RFC 6376）与 ARC（RFC 8617）转发认证链时，若规范化器未按规范自底向上匹配重复头域、忽略正文长度截断参数 `l=` 引发的尾部追加注入，或未校验 `From` 头是否存在多重实例（Multiple-From Spoofing），攻击者可在不破坏原始 DKIM 签名的前提下注入第二个 `From:` 头伪造发件人或在签名正文后追加钓鱼内容。为 Go 邮件安全宿主构建可导入的原始 RFC 5322 字节级 DKIM 与 ARC 认证链验签及反伪造分析包，严禁联网与严禁依赖外部 DKIM 库（仅用标准库 `crypto/rsa`、`crypto/ed25519`、`crypto/sha256`）。组件完整实现 `simple` 与 `relaxed` 两种头域与正文规范化算法（精确处理折行展开、连续空白折叠、尾部空行剥离以及空正文哈希），严格按 RFC 6376 §5.4 自底向上消费 `h=` 列表中的每个头名（准确处理过签 oversigning：当 `h=` 中 `From` 出现次数多于邮件实际 `From` 头数时，多余项对应空字节而不报错，从而有效阻断后续追加新 `From` 头）。安全裁决强制规则包括：拒绝同时存在多个 `From:` 头的邮件、拒绝 `h=` 未覆盖 `From` 的签名、对带 `l=` 正文长度限制且实际正文超出 `l` 字节的邮件明确标为截断注入高危并按策略拒收、严格校验 `x=` 过期时间与 `t=` 签发时间关系；对 ARC 认证链完整验证 `i=1..N` 连续递增（禁止跳号、重复或超 50 跳）、每跳 `ARC-Message-Signature` 与 `ARC-Seal` 签名及 `cv` 状态转换合法性（`i=1` 必为 `none`，后续若出现 `fail` 则整链立即作废）。用真实密钥构造合法及多重 `From`、`l=` 追加、过签突破与断链 ARC 样本实测全检出。
