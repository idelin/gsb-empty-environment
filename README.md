# bitemp-index：双时间轴版本索引

每条记录同时携带两个时间坐标：

| 坐标 | 字段 | 含义 | 对应查询 |
| --- | --- | --- | --- |
| 业务时间（valid time） | `valid_from` / `valid_to` | 事实在业务世界成立的时间 | "10 时发生了什么" |
| 录入时间（transaction time） | `tx_from` | 从哪个观察时刻起该记录作为证据可见 | "当时我们知道什么" |

更正、撤销、补录都以**追加新版本**的方式写入，历史永不改写。查询输入为
`(对象, 业务时间 t, 观察时刻 τ)`，只能看到 `tx_from <= τ` 的证据。

## 语义规则

- **业务区间左闭右开**：`[valid_from, valid_to)`；相接区间 `[0,10)`、`[10,20)`
  中，边界 10 属于后一段。
- **可见性左闭**：`tx_from <= τ` 即可见。
- **重叠优先规则（显式、与到达/遍历顺序无关）**：每条记录内置
  `priority = (tx_from, seq)`，`seq` 是对象内唯一的单调序号。同一对象、同一
  业务时刻的多个可见版本中，priority 最大者胜出；`tx_from` 相同由 `seq`
  决胜。乱序插入得到完全相同的查询结果（有测试保证）。
- **撤销是证据**：`RETRACT` 版本胜出时 `query` 返回该墓碑版本本身，
  `value_at` 将其映射为 `None`（"当时已知此处无值"）。

## 两种时间轴的查询

```python
from bitemp import BitemporalIndex
idx = BitemporalIndex(versions)

idx.query(obj, t_valid=10, t_tx=35)      # 点查询：证据版本
idx.value_at(obj, 10, 35)              # 点查询：值（撤销/无记录 -> None）
idx.timeline(obj, t_tx=45)             # 业务时间轴：截至观察 45 发生了什么
idx.knowledge(obj, 10, [15, 25, 35])   # 录入时间轴：关于 t=10 当时知道什么
```

## 索引结构

按对象分桶，桶内版本按 `(tx_from, seq)` 排序；对每个对象惰性编译一张网格：
每个 `tx_from` 断点对应一份"该观察区间内可见版本解析后的业务时间轴"
（互不重叠的 `Slab` 序列）。一次点查询 = 两次二分查找（先定位观察时刻
所属前缀，再定位业务时刻所属 Slab）。网格是派生结构，新版本到达时仅使
该对象的缓存失效，可随时从 `VersionStore` 重建。

`bitemp.reference` 提供**不依赖索引**的参考查询（全表扫描 + 直接应用语义
规则），`tests/test_bitemp.py` 用随机版本序列（含乱序插入、撤销、未来
版本、相接区间、多次更正）对拍索引与参考实现。

## 旧版本保留与回收条件

- **必须保留**：只要存在某个查询 `(t, τ)` 的答案恰好是该版本。由于可见性
  随 τ 单调增长，一个版本最"容易被看到"的时刻是它自己的录入时刻，因此
  版本 v 是活的 ⟺ 它在 `τ = v.tx_from` 时至少赢得一个业务时刻。
- **可回收（无查询前提）**：v 的整个有效区间在出生时刻就被同 `tx_from`、
  更高 `seq` 的版本覆盖（birth-dominated），则任何查询都不会返回它，
  `gc(versions)` 可安全移除。**注意**：被更晚录入的版本更正/撤销并不使
  旧版本可回收——更早观察时刻的 as-of 查询仍然需要它。
- **地平线压缩（有查询前提）**：若应用保证未来不再使用 `τ < H` 的查询
  （合规/审计保留期决策），`gc(versions, horizon=H)` 把所有
  `tx_from <= H` 的版本压缩为"截至 H 的解析快照"（合成版本，
  `tx_from = H`）。`τ >= H` 的查询答案不变；`τ < H` 的查询不再可回答，
  这正是该模式的前提。
