# 认证恢复渠道双确认

用户替换恢复邮箱时，不能让尚未验证的新邮箱立即拥有找回权。写供Go身份宿主调用的换绑事务包，旧渠道确认与新渠道确认各自绑定同一变更摘要和期限，两者齐备才切换；撤回及并发第二次变更使旧证明失效。用事件排列测试确认乱序、响应丢失和期限边界，任何中间态仍保留明确的恢复渠道。

## 安全模型

- 每次换绑生成一个变更摘要（digest），旧渠道与新渠道的确认令牌均 HMAC 签名并绑定同一 digest 与同一截止时间。
- 两侧确认齐备前，`Active` 始终指向旧渠道；未验证的新渠道在任何中间态都不具备找回权。
- 第二次 `BeginChange` 会取代（supersede）在途事务，撤回（`CancelChange`）会终止事务；二者都让旧 digest 的全部证明立即失效。
- 确认严格按截止时间判定（`now >= expires` 即过期），令牌同时携带自身期限，双期限都未过才接受。
- 响应丢失后的重试幂等；终态后重放返回既成结果或精确的陈旧证明错误，不会重开事务。
- 存储采用版本号 CAS；并发冲突由 Manager 有限次重试，保证原子切换与单一在途事务。

## 包结构

- `channel.go`：渠道、事务、归档、领域事件与哨兵错误。
- `state.go`：纯状态机，承载全部安全不变量（无 I/O，易测试）。
- `token.go`：HMAC-SHA256 确认令牌与变更摘要派生。
- `store.go`：`Store` 接口与 `MemoryStore`（CAS 语义）。
- `manager.go`：宿主调用面（`BeginChange` / `Confirm` / `CancelChange` / `State`）。
- `clock_testing.go`：测试用可控时钟。
- `manager_test.go`：单元测试（期限边界、幂等、撤回、二次变更、令牌伪造、CAS 冲突）。
- `permutation_test.go`：7 个事件的 7! = 5040 种全排列测试，逐步断言不变量并在终态验证重放不动点。
