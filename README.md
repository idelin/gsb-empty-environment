# fsproxy — 可解释的构建文件访问代理

Linux / Python 3.11 标准库实现。构建步骤的所有文件访问都经过 `BuildFSProxy`
这一个收口点：根目录在启动时被固定为一个**目录文件描述符**（dirfd），之后
每个操作都从该 fd 出发逐组件解析并执行，绝不先 `realpath()` 检查再按字符串
打开（那会留下 TOCTOU 窗口）。

本代理是为**合作的**构建步骤提供的访问收口，不声称能够拦截绕过代理直接
进行系统调用的任意进程。

## 公开操作

`read` / `create` / `replace` / `rename` / `unlink` / `list`

- `replace`：在同目录内写临时文件（`.{name}.tmp-*`），`fsync` 后用一次
  `rename(2)` 原子替换；写入失败（含注入失败）会清理临时文件，正式输出
  绝不暴露半成品。
- `rename`：双路径操作，先同时校验源删除权限与目标创建权限，再一次
  `rename(2)` 完成；被拒绝的 rename 不改变任一路径。
- `create`：`O_CREAT|O_EXCL|O_NOFOLLOW`，已存在（含符号链接）即失败。

## 解析与竞态防护（fsproxy/resolver.py）

- 逐组件 `openat` 语义：每个组件相对**已打开的父目录 fd** 打开，链上每个
  目录都由 fd（设备号+inode）钉住。
- 组件用 `O_NOFOLLOW` 打开：检查后被换成符号链接时，open 以 `ELOOP`
  （带 `O_DIRECTORY` 时 Linux 报 `ENOTDIR`）失败，随后显式重新检查并解析，
  绝不隐式跟随。
- 相对符号链接被拼接到剩余组件流中继续解析，跳数上限 40；绝对链接与
  越过根的 `..` 一律拒绝。`..` 对着逻辑祖先栈弹出（我们持有的 fd），
  从不向文件系统询问 `".."`，因此目录被并发改名也不会逃逸。
- 打开后比较 fd 的 `fstat` 身份与检查时的身份；不一致则重解析该组件
  （有界重试，耗尽报 `ResolutionRaceError`）。
- 策略判定作用于**解析后的**根相对路径（符号链接已拼接、`..` 已折叠），
  不是调用方给出的拼写；同前缀兄弟目录（`in` vs `input`）不会误匹配。

## 威胁模型与边界

允许：另一个线程在可写根内替换符号链接、改名普通目录、创建同名路径。
在这些并发下，代理保证不逃逸根、不读写根外对象、不暴露半成品输出。

明确**不包含**（依赖部署环境保证）：

- 修改挂载点（bind mount 移入/移出根）；
- 把已打开的目录移到根之外（`rename(2)` 无法把目录移出其挂载点，且
  攻击者被限制在可写子树内，无法把名字创建进只读子树）；
- 目录在根内被改名后，已钉住的 fd 仍指向同一 inode——操作作用于被授权的
  那个对象本身，审计记录的是该对象的真实设备号与 inode。

## 审计

每个操作（无论成功/拒绝/出错）产生一条 `AuditEvent`：调用路径、解析后
路径、实际操作对象的 `(st_dev, st_ino)`（对最终使用的 fd 做 `fstat` 得到，
**不是**检查时刻的旧路径快照）、结果与拒绝原因。rename 事件同时记录
源与目标两条路径。

## 运行

```bash
python3.11 -m unittest discover -s tests -v   # Linux 全量（含 /proc fd 泄漏测试）
python3.11 examples/demo.py                    # 使用样例
```

## 测试说明

`tests/test_proxy.py` 用 `threading.Event` 屏障精确编排两类交错：

1. “检查组件后、打开组件前”把目录换成符号链接（逃逸版必须被拒绝且根外
   诱饵文件从未被读；根内重定向版必须落到正确对象，且审计记录的是最终
   对象的 inode）；
2. rename 目标在授权后、`rename(2)` 前被并发占用（普通文件被原子替换；
   非空目录使 rename 报错且源、目标均不变）。

另覆盖：根外诱饵文件从未被读写、`a/../b` 解析、同前缀兄弟目录、链接环、
权限交叉（rename 双向权限、只读子树写拒绝且零副作用）、注入写失败不暴露
半成品、文件描述符释放（`/proc/self/fd` 计数，Linux）。

只测静态路径不能当作竞态安全的证明；上述屏障测试只证明这些**具体交错**
被正确处理，竞态安全性最终来自 dirfd + `O_NOFOLLOW` 的设计论证。
