# inbox — 恰好一次业务效果 + 可重发网络输出

业务事件按至少一次语义投递（可能重复）。本库把**去重记录、业务状态修改、
输出消息**放进**同一个本地事务**提交，从而把"业务效果恰好一次"与"网络发送
至少一次"两个关注点分离：

| 关注点 | 保证 | 机制 |
| --- | --- | --- |
| 业务效果 | 恰好一次 | 本地事务内：dedup 记录 + 状态修改 + outbox 入队，原子提交 |
| 网络发送 | 至少一次、可重发 | 提交后再发送；发送与打标分离，崩溃导致回执丢失则恢复后重发 |
| 输出 id | 稳定 | `OutputID(eventID, seq)` = SHA-256 派生，重发 id 不变，接收方按 id 去重 |

## 崩溃恢复语义

```
Handle(event):            DispatchPending():
  ┌─ 本地事务 ─┐            for msg in pending:
  │ InsertDedup│              Send(msg)          ← 网络发送（事务外）
  │ PutState   │  ──提交──▶   ✸ 崩溃点：回执丢失
  │ Enqueue    │              MarkSent(msg.ID)   ← 打标（独立小事务）
  └────────────┘
```

- 崩溃于提交前：事务整体回滚，事件重投后重新处理，效果仍只生效一次。
- 崩溃于提交后、发送前：恢复后 outbox 中仍有待发送消息，补发一次。
- 崩溃于发送后、打标前：恢复后重发**同一条消息（id 相同）**；接收方按
  稳定 id 去重，下游效果仍恰好一次。

## 两个独立持久化模型

同一套崩溃恢复测试套件（`storetest.Run`）对两种模型分别验证：

- `snapshotstore/` — 全量 JSON 快照，tmp 文件 + fsync + 原子 rename；
  崩溃只会留下旧快照或新快照，残留 `.tmp` 被忽略。
- `logstore/` — 追加式 WAL，每次提交一条 `(length, CRC32, payload)` 帧
  并 fsync；恢复时重放有效记录并截断撕裂的尾部记录。

两个模型都要求写穿（write-through）：`Update` 返回即已持久化，不依赖
`Close`，因此测试中"丢弃实例并从同目录重开"即等价于进程崩溃恢复。

## 运行测试

```sh
go test ./...
```

覆盖场景：重复投递去重、提交前崩溃回滚、提交后发送前崩溃补发、
发送后打标前崩溃稳定 id 重发、发送失败重试 id 不变、打标持久化后
不再重发，以及各模型特有的损坏恢复（撕裂 WAL 尾部 / 残留临时快照）。
