# 更新元数据解析一致性

更新代理和设备使用不同JSON解析器，重复键和数字表示可能让两边验证不同版本。给Go更新宿主实现规范消息接收包，版本和长度仅允许无前导零的十进制整数，拒绝重复键、未知关键字段及超范围数，字段顺序可变但摘要按统一规范编码。用两套独立解析路径比较合法输入语义，变形样本必须在发布前拒绝。

## 消息信封

接收的顶层值必须是 JSON 对象，且只包含以下四个字段，缺一不可、多一不可：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `version` | 整数 | 规范十进制，取值在 `uint32` 范围内 |
| `length` | 整数 | 规范十进制，取值在 `uint64` 范围内，且等于 `payload` 解码后的字节数 |
| `payload` | 字符串 | 标准 base64（`StdEncoding`，带填充）解码后的载荷 |
| `digest` | 字符串 | 恰好 64 个小写十六进制字符的 SHA-256 摘要 |

字段在线上可以按任意顺序出现；对象内出现重复键（含经 `\uXXXX` 转义后等价的键名）一律拒绝，出现未知键一律拒绝。

## 规范整数与规范编码

`version` 与 `length` 只接受规范十进制整数：

- 允许 `0` 以及首位为 `1-9` 的数字串；禁止前导零（`07`、`00`）。
- 禁止符号（`-1`、`+1`）、小数（`7.0`）、指数（`1e1`）和十六进制（`0x1`）。
- 超出声明位宽的数字以 `ErrOutOfRange` 拒绝，而不是静默截断。

摘要与重新编码使用统一的规范形式，与输入字段顺序、空白和转义风格无关：

- 固定键序 `version,length,payload,digest`，紧凑分隔符（无空白）。
- 整数按规范十进制输出，`payload` 按标准 base64 规范化输出。
- 字符串只做 JSON 必需的最小转义，不做 HTML 转义。
- `digest = lowercase_hex(sha256(canonical_core))`，其中 `canonical_core` 是不含 `digest` 字段本身的前三个字段规范编码。

## 双解析路径

`Receive` 使用两条互不共享解析代码的路径，任何一条拒绝即整体拒绝：

1. `parse_hand`：手写字节级递归下降解析器，保留全部键出现记录与数字原文。
2. `parse_std`：仅基于标准库 `encoding/json` 的 token 流，`UseNumber` 保留数字原文，同样保留重复键。

两条路径产出统一的中间表示后做深度比较；语义不一致返回 `ErrParserDivergence`。数字形状、取值范围、schema 与摘要校验只在共享代码中实现一次，确保两边套用完全相同的规则。输入必须为合法 UTF-8。

## 发布前拒绝的变形样本

`TestReceiveMutationsRejected` 是发布闸门，覆盖：前导零/符号/小数/指数数字、超范围整数、重复键、未知字段、缺失字段、错误类型（字符串/数组/null）、长度与载荷不符、非法 base64、非小写或长度错误的摘要、被篡改的摘要或载荷、尾随数据、BOM、单引号、未加引号的键、尾随逗号以及非法 UTF-8。

`TestParserAgreement` 对随机合法信封、字节级变异样本和随机噪声各跑 200 轮，断言两条路径的接受/拒绝结论与解析语义始终一致。
