实时音视频与物联网网关运行 DTLS 1.2/1.3（RFC 6347 / RFC 9147）时，若服务端在收到初始 `ClientHello` 后直接回复包含大证书链的 `ServerHello` 而未先执行无状态 `HelloVerifyRequest` Cookie 交换，攻击者可伪造受害者源 IP 发动数十倍 UDP 反射放大；若记录层在 `Epoch` 切换时未按每个 `Epoch` 独立维护 48 位序列号防重放滑动窗口、允许旧 `Epoch` 明文记录在切换到加密 `Epoch` 后继续被当作当前握手消息接受，或未在认证通过前锁定窗口，攻击者可发动跨 Epoch 降级或重放攻击。为 Go 传输安全宿主实现可导入的 DTLS 无状态 Cookie 防放大与多 Epoch 48 位记录层防重放状态机包，严禁联网（仅用标准库 `crypto/hmac`/`crypto/sha256`/`crypto/aes`/`crypto/cipher`）。组件严格实现：（1）无状态 `HelloVerifyRequest` Cookie 交换：基于轮换密钥与 `(client_ip, client_port, client_version, client_random, cipher_suites_hash, epoch_bucket)` 生成 HMAC-SHA256 Cookie；未携带合法 Cookie 的 `ClientHello` 仅回复极短 `HelloVerifyRequest`（严禁发出证书），硬拒绝跨 IP/端口重放、过期或篡改套件的 Cookie；（2）每 Epoch 独立 48 位序列号防重放滑动窗口（支持 64/256 位位图）：在 AEAD 认证（含 13 字节记录头 AAD：`epoch || seq_num || type || version || length`）通过**后**才推进该 Epoch 窗口与右边界，硬拒绝 48 位序列号回绕溢出（`2^48-1` 强制 Rekey）；（3）严格 Epoch 隔离与降级阻断：切换到新加密 Epoch 后硬拒绝再从 `Epoch 0` 接受任何非允许重传的握手/应用记录，防止明文注入覆盖已认证状态。附未带 Cookie 放大阻断、跨 IP Cookie 盗用、跨 Epoch 明文降级、未认证高序列号推飞阻断与重放测试。
