# SCT数量与运营方多样性门槛

证书里嵌入的 SCT 要来自足够多且互相独立的日志，攻击者可让同一运营方的多个日志各出一份，或重复提交同一份 SCT 凑数。给Go证书校验包写供握手后回调使用的 SCT 策略组件，签名验证与日志表由调用方注入，以下为本题规定：有效期不超过 180 天的证书至少 2 份有效 SCT，超过 180 天的至少 3 份；有效 SCT 须来自至少两个不同运营方；同一 log_id 只计一份；日志状态为已退休且 SCT 时间戳晚于退休时间、或被拒绝、或待收录的不计；时间戳晚于验证时间 5 分钟以上的不计；SCT 版本不是 v1 的不计。用同运营方多日志、重复 SCT、退休后时间戳和 180 天边界验证。

## 组件

- `SCTPolicy`：策略主体，`LogTable`（日志表）与 `SignatureVerifier`（签名验证）由调用方通过接口注入，`Now` 可注入固定时钟。
- `Evaluate(cert, scts)`：返回 `SCTReport`，策略不满足时返回可 `errors.Is` 匹配的 `ErrTooFewSCTs` / `ErrTooFewOperators`（`*PolicyError` 携带完整报告）。
- `VerifyConnection`：签名适配 `tls.Config.VerifyConnection`，优先使用握手下发的 SCT，回退到证书 OID 1.3.6.1.4.1.11129.2.4.2 内嵌扩展。
- `ParseSCTList` / `ParseSCT`：RFC 6962 线格式解析。

## 规则

- 有效期恰好 180 天按“不超过”处理，门槛 2 份；超过 180 天门槛 3 份。
- 仅版本为 v1、时间戳不晚于验证时间 5 分钟、日志状态允许且签名通过的 SCT 计入。
- 已退休日志在退休时间点及更早签发的 SCT 仍有效，晚于退休时间的不计；被拒绝、待收录日志的 SCT 一律不计。
- 同一 `log_id` 只计一份，重复项在报告中标记为 `RejectDuplicate`；有效 SCT 须覆盖至少两个运营方。

